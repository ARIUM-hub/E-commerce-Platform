# 袜子商城后台订单状态流转设计

- 日期：2026-07-31
- 阶段：后台订单操作闭环
- 范围：确认发货、订单取消、按商品部分退款、售后审核、库存回补与操作审计

## 1. 目标

把现有后台订单页从“推进演示状态”升级为可解释、可校验、可追踪的订单处理工作台。管理员需要通过明确的业务动作处理订单，而不是直接修改状态值；每次动作都必须由后端验证当前状态，并在同一事务中更新订单、履约、退款、售后、库存和审计记录。

本阶段继续使用本地 SQLite 和演示管理员权限，不接真实物流商或支付退款网关，但数据结构和接口边界为后续接入外部服务保留替换空间。

## 2. 已确认的业务决策

- 退款支持按订单商品和数量进行部分退款。
- 退货退款在售后完成时回补对应 SKU 库存。
- 仅退款不回补库存。
- 未发货订单取消产生退款时，回补订单中的全部 SKU 库存。
- 部分退款既可从已审核售后单发起，也可由管理员从订单后台直接发起。
- 直接部分退款必须填写退款原因。
- 确认发货时由管理员选择承运商并填写运单号。
- 运单号必填且全局唯一。
- 已发货或已送达订单不能直接取消，必须进入售后流程。

## 3. 现有基础与缺口

项目当前已有：

- SQLite 持久化订单、履约、退款、售后、SKU 库存和支付数据。
- 订单、履约、退款和售后各自的状态流转规则。
- 后台订单列表及“推进订单、推进物流、推进退款”按钮。
- 用户侧订单详情、物流轨迹、退款进度和售后进度。

当前缺口：

- 后台按钮只有下一状态，没有发货、取消、退款等业务上下文。
- 确认发货不能录入承运商和真实运单号。
- 退款只支持订单级金额，不能记录退款商品和数量。
- 后台没有完整的售后列表和审核入口。
- 库存回补缺少统一来源、幂等标识和流水记录。
- 后台关键操作缺少管理员、原因和状态前后值的审计记录。

## 4. 推荐架构

新增 `lib/repositories/admin-order-actions.js`，作为后台订单业务动作的唯一入口。模块提供四类命令：

- `shipOrder`：确认发货。
- `cancelOrderByAdmin`：后台取消订单。
- `createPartialRefund`：创建按商品部分退款。
- `reviewReturnRequest`：审核售后申请。

该模块负责：

- 校验管理员动作请求。
- 校验订单、履约、退款和售后状态。
- 计算可退款数量与可退款金额。
- 在 SQLite 事务内调用现有仓储并写入关联数据。
- 写入库存流水和后台操作审计。
- 使用操作 ID 实现幂等。

现有订单、履约、退款和售后仓储继续负责各自数据的读取和序列化。新模块负责编排，不复制已有状态模型。

## 5. 数据模型升级

### 5.1 `refund_items`

记录退款对应的订单商品：

- `id`
- `refund_id`
- `order_id`
- `product_id`
- `sku_id`
- `title`
- `size`
- `quantity`
- `unit_paid_amount`
- `refund_amount`
- `created_at`

`unit_paid_amount` 来自订单创建时保存的商品与优惠快照，不读取当前商品价格。

### 5.2 `inventory_movements`

记录库存变化来源：

- `id`
- `sku_id`
- `product_id`
- `quantity_delta`
- `reason`
- `source_type`
- `source_id`
- `operation_id`
- `created_at`

`operation_id + sku_id + reason` 建立唯一约束，防止重复回补。

### 5.3 `admin_action_events`

记录后台关键操作：

- `id`
- `operation_id`
- `admin_user_id`
- `action`
- `resource_type`
- `resource_id`
- `reason`
- `before_status`
- `after_status`
- `payload`
- `created_at`

`operation_id` 唯一。重复请求返回第一次操作的结果，不重复执行副作用。

### 5.4 现有表调整

- `refunds` 增加可选 `return_request_id`、`operation_id` 和退款类型字段。
- `fulfillments.tracking_number` 增加唯一索引；空值不参与唯一性校验。
- `return_requests` 保持现有状态，不再增加重复的退款状态字段；关联退款通过 `refunds.return_request_id` 查询。

## 6. 状态与业务规则

### 6.1 确认发货

仅允许订单从 `processing` 进入 `shipped`：

1. 校验承运商属于允许列表。
2. 校验运单号非空且未被使用。
3. 更新订单主状态为 `shipped`。
4. 更新履约状态为 `label_created`。
5. 保存承运商、运单号和首条物流轨迹。
6. 写入订单时间线和后台审计记录。

同一 `operationId` 重复提交返回原结果。不同操作 ID 重复发货返回 `ADMIN_ORDER_ALREADY_SHIPPED`。

### 6.2 后台取消订单

- `pending_payment`：变为 `cancelled`，不创建退款。
- `paid` 或 `processing`：变为 `refund_pending`，创建整单退款，并按订单商品数量回补库存。
- `shipped` 或 `delivered`：拒绝取消，提示进入售后流程。
- `cancelled`、`refund_pending` 或 `refunded`：拒绝重复取消。

取消原因必填。已支付订单的整单退款金额使用订单支付成功时的实付总额，包含订单快照中的税费和运费。

### 6.3 按商品部分退款

管理员从订单商品中选择一个或多个 SKU，并填写数量、退款金额和原因。

校验规则：

- 订单必须已支付，且不能处于 `cancelled` 或 `refunded`。
- SKU 必须来自订单快照。
- 单个 SKU 累计退款数量不能超过购买数量。
- 商品累计退款金额不能超过该商品分摊后的折后实付金额。
- 订单累计退款金额不能超过订单实付金额。
- 默认可退金额不包含运费和税费。
- 后台允许降低实际退款金额，但不能超过本次选择商品的剩余可退上限。
- 退款原因必填。

订单行实付分摊规则：

1. 使用订单商品原始小计。
2. 按商品小计占比分摊商品级和订单级优惠。
3. 金额统一以分为整数计算。
4. 最后一行承担四舍五入产生的尾差。

创建部分退款后，订单保持原履约状态；退款进度由独立退款记录展示。只有整单可退余额全部完成时，订单才同步为 `refunded`。

### 6.4 售后审核

状态流保持：

- `submitted -> reviewing`
- `reviewing -> approved`
- `reviewing -> rejected`
- `approved -> completed`

规则：

- 开始审核不创建退款。
- 审核通过退货退款或仅退款时，可在同一操作中创建关联退款。
- 拒绝时必须填写原因。
- 完成退货退款时回补售后商品对应 SKU 库存。
- 完成仅退款时不回补库存。
- 换货本阶段只完成审核状态，不自动创建新订单或新物流单。
- 已完成、已拒绝或已取消的售后不能再次处理。

## 7. 库存一致性

库存变化只通过事务化库存流水执行：

- 后台取消未发货已支付订单：回补全部订单 SKU。
- 退货退款售后完成：回补售后申请中的 SKU 和数量。
- 仅退款：不回补。
- 直接部分退款：默认不回补，避免把未实际退回的商品重新计入可售库存。

每次回补先写入唯一库存流水，再更新 `product_variants.stock_quantity`。如果流水已存在，返回原结果，不重复增加库存。

## 8. API 设计

### 8.1 确认发货

`POST /api/admin/orders/:id/actions/ship`

```json
{
  "operationId": "op-ship-001",
  "carrier": "ups",
  "trackingNumber": "1Z999AA10123456784",
  "note": "仓库已交接承运商",
  "locale": "zh-CN"
}
```

### 8.2 取消订单

`POST /api/admin/orders/:id/actions/cancel`

```json
{
  "operationId": "op-cancel-001",
  "reason": "customer_request",
  "note": "客户通过客服要求取消",
  "locale": "zh-CN"
}
```

### 8.3 创建部分退款

`POST /api/admin/orders/:id/actions/refund`

```json
{
  "operationId": "op-refund-001",
  "reason": "quality_issue",
  "note": "商品局部瑕疵补偿",
  "returnRequestId": "",
  "items": [
    {
      "skuId": "sock-01-40",
      "quantity": 1,
      "refundAmount": 1299
    }
  ],
  "locale": "zh-CN"
}
```

金额字段使用整数分，避免浮点误差。

### 8.4 审核售后

`POST /api/admin/returns/:id/actions/review`

```json
{
  "operationId": "op-return-001",
  "action": "approve",
  "reason": "evidence_confirmed",
  "note": "审核通过",
  "refundItems": [
    {
      "skuId": "sock-01-40",
      "quantity": 1,
      "refundAmount": 1299
    }
  ],
  "locale": "zh-CN"
}
```

允许动作：`start_review`、`approve`、`reject`、`complete`。

### 8.5 后台售后列表

`GET /api/admin/returns?status=&q=`

返回售后摘要、申请商品、关联退款、可执行动作和时间线。

## 9. 后台界面

### 9.1 订单标签页

订单列表保持高密度运营风格，每行展示：

- 订单号与客户。
- 订单、支付、履约和退款状态。
- 实付金额。
- 创建时间。
- “处理订单”按钮。

点击后打开操作抽屉，抽屉展示：

- 订单商品和各 SKU 数量。
- 支付与可退款摘要。
- 物流信息。
- 已有退款记录。
- 订单与后台操作时间线。
- 当前状态允许的操作表单。

### 9.2 操作表单

确认发货：

- 承运商选择。
- 运单号输入。
- 可选备注。
- 确认发货按钮。

取消订单：

- 取消原因。
- 可选备注。
- 展示是否会退款和回补库存。
- 二次确认按钮。

部分退款：

- 每个 SKU 的购买数量、已退数量和剩余可退数量。
- 本次退款数量。
- 可退金额上限。
- 本次退款金额。
- 退款原因和备注。

### 9.3 售后标签页

新增后台“售后”标签页：

- 支持按状态和订单号筛选。
- 展示售后单号、订单号、用户、类型、原因、状态和创建时间。
- 操作抽屉展示申请商品、说明、时间线和关联退款。
- 根据状态显示开始审核、通过、拒绝或完成操作。

### 9.4 交互与可访问性

- 抽屉使用语义化对话框，打开后聚焦标题，关闭后焦点返回触发按钮。
- 所有输入都有可见标签和内联错误。
- 提交期间禁用当前表单，避免重复操作。
- 危险操作使用明确的二次确认，不使用浏览器原生 `alert` 或 `confirm`。
- 状态不能只靠颜色区分，同时展示文字标签。
- 移动端抽屉占满视口宽度，桌面端限制为可读宽度。

## 10. 错误处理

继续使用标准错误信封。新增错误码：

- `ADMIN_ORDER_ACTION_INVALID`
- `ADMIN_ORDER_TRANSITION_INVALID`
- `ADMIN_ORDER_ALREADY_SHIPPED`
- `ADMIN_ORDER_CANCEL_NOT_ALLOWED`
- `ADMIN_CARRIER_INVALID`
- `ADMIN_TRACKING_REQUIRED`
- `ADMIN_TRACKING_DUPLICATE`
- `ADMIN_REFUND_ITEMS_REQUIRED`
- `ADMIN_REFUND_QUANTITY_INVALID`
- `ADMIN_REFUND_QUANTITY_EXCEEDED`
- `ADMIN_REFUND_AMOUNT_INVALID`
- `ADMIN_REFUND_AMOUNT_EXCEEDED`
- `ADMIN_REFUND_REASON_REQUIRED`
- `ADMIN_RETURN_ACTION_INVALID`
- `ADMIN_RETURN_TRANSITION_INVALID`
- `ADMIN_RETURN_REASON_REQUIRED`
- `ADMIN_OPERATION_DUPLICATE_MISMATCH`

同一操作 ID 和相同请求内容重复提交时返回首次结果；同一操作 ID 携带不同内容时返回 `ADMIN_OPERATION_DUPLICATE_MISMATCH`。

## 11. 前台同步

后台操作后，用户侧无需维护第二份状态：

- 订单详情读取更新后的订单、履约和退款记录。
- 售后详情读取更新后的售后时间线和关联退款。
- 库存列表读取回补后的 SKU 库存。
- 订单历史显示最新订单状态和退款摘要。

本阶段不增加实时推送。用户刷新或重新进入页面即可读取最新状态。

## 12. 测试策略

采用 TDD，每项业务先写失败测试，再实现最小代码。测试保持 Playwright 单 worker。

### 12.1 API 测试

- 处理中订单可填写承运商和唯一运单号确认发货。
- 非处理中订单不能确认发货。
- 重复运单号被拒绝。
- 同一发货操作 ID 重复请求不重复创建轨迹。
- 待支付订单取消后无退款。
- 已支付未发货订单取消后创建整单退款并回补库存。
- 已发货订单不能取消。
- 部分退款记录 SKU、数量和整数分金额。
- 超过购买数量、商品可退金额或订单实付金额的退款被拒绝。
- 多次部分退款正确累计剩余数量和金额。
- 直接部分退款不回补库存。
- 售后开始审核、通过、拒绝和完成遵循合法状态流。
- 退货退款完成只回补一次库存。
- 仅退款完成不回补库存。
- 非管理员不能调用后台动作接口。
- 重复操作 ID 不重复执行，内容不一致时返回冲突错误。

## 13. 验收标准

- 管理员能填写承运商和唯一运单号确认发货。
- 管理员能按规则取消未发货订单。
- 管理员能按 SKU 和数量创建不超额的部分退款。
- 管理员能从订单或已审核售后单发起退款。
- 管理员能完成售后开始审核、通过、拒绝和完成操作。
- 库存仅在约定场景回补，重复请求不会重复增加库存。
- 所有后台关键操作都有管理员、原因、前后状态和时间记录。
- 用户侧订单、物流、退款和售后状态与后台处理结果一致。
- 新增功能不破坏现有支付、履约、购物车和库存流程。

## 14. 明确不做

- 不接真实物流商 API。
- 不接真实支付退款网关。
- 不做换货新订单和逆向物流单。
- 不做退款运费、税费的手工分摊编辑器。
- 不做多仓库或多包裹拆分发货。
- 不做复杂 RBAC，继续使用现有演示管理员权限。
- 不做 WebSocket 或实时状态推送。
- 不进行高并发、压力测试或批量供应商请求。

## 15. 自检

- 范围只覆盖后台订单与售后状态流转，没有混入商品、营销或客服扩展。
- 部分退款数量、金额和库存规则均有唯一解释。
- 发货、取消、退款和售后审核使用明确动作，不再依赖任意状态修改。
- 所有会产生副作用的动作都有事务、幂等和审计要求。
- API、数据模型、界面和测试验收标准相互对应。
- 文档不存在占位符、未决项或 Unicode 转义字符。
