# 袜子商城真实结算流程与订单生命周期设计

## 目标

把当前袜子商城从“购物车演示”升级为“可跑通订单闭环”的真实商城体验。采用演示级真实结算闭环：用户从购物车进入结算页，填写收货信息，选择配送方式，提交订单，后端生成持久化订单，前端展示订单详情与订单状态时间线。

## 当前基础

- 已有商品列表、详情页、分类、搜索、排序、多语言和共享商城壳层。
- 已有购物车 JSON 后端接口：读取、加购、更新数量、移除、清空。
- 已有库存上限校验和无货提示。
- 已有订单确认/订单页雏形，但目前订单更偏前端快照，缺少真实订单持久化与生命周期。

## 范围

第一阶段只做匿名用户的真实结算闭环，不做账号系统、真实支付网关、后台管理和数据库迁移。

本阶段包含：
- 新增 checkout 视图：`/socks-product-list.html?view=checkout`。
- 购物车抽屉点击 `去结算` 跳转 checkout，而不是直接清空购物车。
- Checkout 表单收集收货信息：姓名、手机号/邮箱、地址、城市、省/州、邮编、配送备注。
- 配送方式选择：标准配送、加急配送，影响运费、预计送达和订单总价。
- 后端新增订单持久化：`data/orders.json` 与测试 fixture 对应文件。
- 后端新增订单 API：创建订单、读取订单、更新订单状态。
- 订单详情页展示订单快照、金额、收货信息、配送方式和状态时间线。
- 订单创建成功后清空购物车，但订单商品明细保留创建时快照。
- 订单生命周期支持：待支付、已支付、处理中、已发货、已送达、已取消。

## 不包含

- 用户登录、注册、地址簿。
- 真实第三方支付。
- 真实物流查询。
- 管理后台。
- 数据库替换 JSON 文件。
- 邮件、短信通知。

## 页面与交互

### 购物车到结算

购物车非空时，`去结算` 按钮跳转到 checkout 视图。空购物车时按钮保持禁用。进入 checkout 后仍保留顶部导航和页脚，保持当前商城壳层一致。

### Checkout 视图

Checkout 视图采用左右布局：
- 左侧为结算表单和配送方式。
- 右侧为订单摘要，包含商品、尺码、数量、原价小计、优惠、运费、预计总计。

移动端降为单列，订单摘要在表单之后展示。

表单字段：
- 姓名，必填。
- 联系方式，必填，接受手机号或邮箱形式。
- 地址，必填。
- 城市，必填。
- 省/州，必填。
- 邮编，必填。
- 配送备注，选填。

配送方式：
- 标准配送：运费默认 0，预计 3-5 天。
- 加急配送：运费默认 12，预计 1-2 天。

提交按钮：
- 购物车为空时禁用并提示返回商城加购。
- 表单缺失必填项时显示字段级错误。
- 提交中禁用按钮，避免重复创建订单。
- 成功后跳转订单详情视图。

### 订单详情视图

订单详情视图通过 `?view=order&id=<orderId>` 打开。内容包括：
- 订单号。
- 当前状态。
- 状态时间线。
- 收货信息。
- 配送方式和预计送达。
- 商品快照。
- 金额汇总。
- 操作按钮。

演示操作按钮：
- 待支付：模拟付款、取消订单。
- 已支付：模拟处理中。
- 处理中：模拟发货。
- 已发货：模拟送达。
- 已送达/已取消：只展示状态，不提供继续推进。

## 后端 API

### `POST /api/orders`

从当前购物车创建订单。

请求体包含：
- `customer`
- `shippingAddress`
- `shippingMethodId`

后端校验：
- 购物车不能为空。
- 商品仍存在。
- 尺码仍有效。
- 商品总数量不超过库存。
- 必填收货字段完整。
- 配送方式有效。

成功响应：
- `201`
- 返回 `{ order, cart }`
- 订单写入 `orders.json`
- 购物车写回空数组

失败响应：
- `400 CHECKOUT_VALIDATION_FAILED`
- `409 OUT_OF_STOCK`
- `404 PRODUCT_NOT_FOUND`

### `GET /api/orders/:id`

读取单个订单详情。

成功响应：
- `200 { order }`

失败响应：
- `404 ORDER_NOT_FOUND`

### `PATCH /api/orders/:id/status`

推进订单状态。

请求体：
- `status`

允许流转：
- `pending_payment -> paid`
- `pending_payment -> cancelled`
- `paid -> processing`
- `processing -> shipped`
- `shipped -> delivered`

失败响应：
- `400 INVALID_ORDER_STATUS`
- `409 INVALID_ORDER_TRANSITION`
- `404 ORDER_NOT_FOUND`

## 前端状态与数据流

1. 用户从商品页加购。
2. 购物车抽屉读取真实 cart state。
3. 点击去结算进入 checkout 视图。
4. Checkout 初始化时读取购物车和商品信息。
5. 用户填写地址并选择配送方式。
6. 提交订单调用 `POST /api/orders`。
7. 成功后前端同步空购物车，并跳转 `?view=order&id=<orderId>`。
8. 订单详情通过 `GET /api/orders/:id` 渲染。
9. 演示状态按钮调用 `PATCH /api/orders/:id/status`。

## UI 原则

- 延续当前黑、白、灰的高信息密度商城风格。
- Checkout 表单必须有可见 label，不能只依赖 placeholder。
- 必填错误显示在对应字段附近。
- 提交按钮有 pending/disabled 状态。
- 订单时间线清晰展示当前状态。
- 移动端保持单列、无横向滚动。

## 测试重点

后端测试：
- 空购物车不能创建订单。
- 缺少必填地址字段不能创建订单。
- 库存不足不能创建订单。
- 成功创建订单会写入 `orders.json` 并清空 `cart.json`。
- 订单状态只能按允许流转推进。

前端测试：
- 非空购物车点击去结算进入 checkout。
- Checkout 展示购物车商品和金额汇总。
- 缺少必填字段展示错误，不创建订单。
- 成功提交后跳转订单详情，购物车归零。
- 订单详情显示状态时间线和商品快照。
- 模拟付款/发货/送达会更新订单状态。

## 验收标准

- 用户能从列表或详情加购商品。
- 用户能从购物车进入 checkout。
- 用户能填写地址并创建持久化订单。
- 创建订单后购物车被清空。
- 刷新订单详情页后订单仍存在。
- 订单状态能按生命周期推进。
- 关键流程有自动化测试覆盖。
