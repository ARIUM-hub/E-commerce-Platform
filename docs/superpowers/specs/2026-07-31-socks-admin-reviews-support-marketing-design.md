# 评论管理、客服工单与优惠活动配置设计

## 目标

在现有商城后台中增加三个可独立交付的运营子系统：评论管理、客服工单处理和优惠活动可视化配置。三个模块复用现有管理员认证、SQLite 事务、标准错误码、幂等操作与审计机制，同时保持各自的数据模型、状态流、路由和界面边界清晰。

实施顺序固定为：

1. 评论管理。
2. 客服工单处理。
3. 优惠活动可视化配置。

每个阶段都必须具备独立迁移、API、后台界面和自动化测试，不以未完成的后续阶段作为当前阶段的运行前提。

## 现状

- 商品评论已支持前台提交、评分筛选、排序、买家晒图字段、Verified Purchase、差评原因标签和“有帮助”投票，但没有审核状态、商家回复和后台管理接口。
- 客服中心已支持匿名或登录用户创建工单，工单只有 `open` 状态，后台看板只读取未关闭数量，没有分配、回复、内部备注和客户追踪能力。
- 优惠券、促销和组合购买已有运行表及前台价格计算，后台只能查看并启停，缺少草稿、编辑、排期、冲突检测、预览和版本历史。
- 后台使用顶部模块页签、高密度列表和右侧操作抽屉，视觉语言为黑、白、灰。

## 总体架构

采用共享后台操作平台方案。评论、工单和优惠分别使用独立 repository、route 和前端管理模块，复用以下基础设施：

- `requireAdmin` 管理员权限校验。
- `operationId` 幂等请求约束。
- SQLite 原子事务。
- 标准 `{ error: { code, message, fields? } }` 错误响应。
- `admin_action_events` 操作审计。
- 后台页签、筛选栏、表格、右侧抽屉、内联错误和焦点恢复模式。

新功能不得继续集中堆入 `server.js` 和 `public/js/storefront-app.js`。服务端通过独立路由注册模块接入，浏览器端通过独立后台模块挂载到现有页面。现有商城运行 API 保持兼容。

## 评论管理

### 发布规则

评论采用混合审核：

- 已登录用户且通过本地规则校验的评论自动进入 `published`。
- 匿名评论默认进入 `pending`。
- 已登录用户命中风险规则时也进入 `pending`。
- 风险规则只使用本地确定性判断，包括重复内容、外链、非法长度和短时间高频提交，不调用外部模型服务。
- 商品页只展示 `published` 评论；评分汇总和评论数只统计 `published`。
- 历史评论迁移后默认设为 `published`，保持现有商品页数据不变。

### 状态流

评论状态为：

- `pending`：待审核，可转为 `published` 或 `rejected`。
- `published`：前台可见，可转为 `hidden`。
- `hidden`：前台不可见，可恢复为 `published`。
- `rejected`：审核拒绝，普通管理操作不可恢复。

拒绝和隐藏必须填写结构化原因，可附加备注。违法内容删除作为独立审计级操作，不纳入普通批量操作。
批量审核在单个事务中执行，任何一条评论状态不合法时整批回滚，并返回冲突评论 ID。

### 数据模型

扩展 `product_reviews`：

- `user_id`、`session_id`：提交主体。
- `status`：审核状态。
- `moderation_reason`、`moderation_note`：最后一次审核结果。
- `moderated_by`、`moderated_at`、`updated_at`。
- `risk_flags`：本地规则命中的结构化标记。

新增 `product_review_replies`：

- 一条评论最多一条当前商家回复。
- 保存回复正文、管理员、创建时间、更新时间和撤回时间。
- 编辑和撤回通过审计事件保留历史，不物理覆盖审计记录。

### 后台能力

- 按商品、评分、状态、是否已回复、是否 Verified Purchase 和提交时间筛选。
- 搜索评论正文、作者和商品名。
- 单条或批量通过、拒绝、隐藏和恢复。
- 新增、编辑和撤回商家回复。
- 抽屉展示完整评论、买家信息、晒图、风险标记、审核历史和回复。
- 看板增加待审核评论和低评分评论 KPI。

## 客服工单处理

### 状态流

工单状态为：

- `open`：待处理。
- `in_progress`：处理中。
- `waiting_customer`：等待客户补充信息。
- `resolved`：已解决，可由客户或客服重新打开到 `in_progress`。
- `closed`：已关闭，不允许继续回复；如需继续处理，创建新工单并关联原工单。

客户在 `waiting_customer` 状态回复后，工单自动转为 `in_progress`。所有状态变化记录操作者、时间和原因。

### 数据模型

扩展 `support_tickets`：

- `priority`：`low / normal / high / urgent`。
- `assigned_admin_user_id`。
- `resolved_at`、`closed_at`、`last_message_at`。
- `version`：并发更新检查。
- `parent_ticket_id`：关闭后创建后续工单时关联原工单。

新增 `support_ticket_messages`：

- `visibility`：`public` 或 `internal`。
- `author_type`：`customer` 或 `admin`。
- `author_user_id`、正文和创建时间。
- 内部备注永远不返回客户侧接口。

新增 `support_ticket_events`：保存状态、优先级和处理人变更记录。

### 客户侧追踪

- 登录用户可以查看自己的工单列表、工单详情、公开时间线并补充消息。
- 匿名用户使用工单号和标准化联系方式查询。
- 匿名查询失败需要限频，错误响应不泄露工单是否存在或联系方式是否匹配。
- 客户只能读取公开消息，不能读取处理人内部信息、内部备注或后台审计载荷。

### 后台能力

- 按状态、优先级、主题、处理人、订单号和更新时间筛选。
- 搜索工单号、联系信息和消息正文。
- 设置优先级和处理人。
- 发送公开回复或内部备注，两种输入区使用明显不同的视觉提示。
- 推进状态、重新打开已解决工单并查看完整事件时间线。
- 看板增加未分配、紧急、等待客户和超时工单 KPI。

## 优惠活动可视化配置

### 覆盖类型

第一阶段只覆盖现有运行类型：

- 优惠券。
- 满减与限时折扣促销。
- 组合购买。

不在本阶段新增秒杀、会员价、推荐位或多管理员审批。

### 状态流

活动配置状态为：

- `draft`：草稿，可编辑。
- `scheduled`：已排期，尚未开始。
- `active`：当前生效。
- `paused`：已暂停，可恢复为排期或生效状态。
- `ended`：已结束，不可直接编辑，只能复制为新草稿。

开始和结束时间由服务端当前时间判断，商城读取接口只返回处于有效窗口且未暂停的运行数据。
系统不启动常驻定时任务。后台活动列表和商城营销读取前调用同一个状态协调函数，在事务中把到期的 `scheduled` 转为 `active`、把超过结束时间的 `active` 转为 `ended`，并以系统操作者写入审计事件。暂停活动恢复时，开始时间未到则回到 `scheduled`，当前处于有效窗口则回到 `active`，已经超过结束时间则拒绝恢复。

### 草稿与运行投影

保留现有 `promotions`、`coupons` 和 `bundles` 作为商城价格计算的运行表。新增活动配置与版本存储：

- `marketing_campaigns`：活动身份、类型、状态和当前版本。
- `marketing_campaign_versions`：每次草稿保存或发布的完整规则快照、版本号、创建人和时间。

后台编辑版本草稿。发布时在单个事务内完成校验、保存发布版本并更新对应运行表。运行表写入失败时，发布状态和版本不得部分提交。

### 发布校验

- 优惠值、最低消费和数量必须处于合法范围。
- 开始时间早于结束时间。
- 商品 ID 和 SKU 必须存在且可售。
- 组合购买商品和默认尺码必须完整。
- 同一商品范围和时间窗口内的互斥活动不得重叠。
- 优惠券可以并存，但券码必须唯一且每个购物车只能应用一张；同一价格层级、商品范围和时间窗口重叠的促销互斥；包含相同商品集合的组合购买在重叠时间内互斥。
- 发现冲突时阻止发布，并返回冲突活动 ID、名称和字段，不静默覆盖。
- 草稿保存使用 `version` 乐观锁，旧页面提交返回 `MARKETING_VERSION_CONFLICT`。

### 后台能力

- 活动列表按类型、状态、时间和商品范围筛选。
- 创建、编辑、复制、排期、发布、暂停、恢复和结束活动。
- 编辑流程分为基础信息、优惠规则、适用商品、排期和预览发布。
- 预览使用与购物车价格计算相同的服务函数，展示示例商品、原价、优惠拆分和最终价格。
- 展示版本历史和发布审计，但第一阶段不提供任意旧版本直接回滚；需要复制旧版本为新草稿后重新发布。

## 界面设计

采用已确认的顶部模块页签、高密度表格和右侧操作抽屉布局。

### 评论页签

- 顶部 KPI：待审核、已发布、隐藏、低评分。
- 筛选栏与批量选择位于列表上方。
- 处理抽屉显示评论内容、媒体、风险提示、审核操作和商家回复。

### 工单页签

- 顶部 KPI：未分配、紧急、等待客户、超时。
- 列表突出优先级、状态、主题、处理人和最近更新时间。
- 抽屉使用消息时间线，公开回复和内部备注分区。

### 优惠页签

- 列表保留快速状态查看，移除直接无确认启停。
- “创建活动”打开分段编辑抽屉。
- 桌面端右侧实时价格预览，375px 移动端改为单列。

### 客户工单页面

- 帮助中心增加查询入口。
- 登录用户直接进入工单历史；匿名用户显示工单号与联系方式查询表单。
- 详情展示公开时间线、当前状态和补充消息表单。

所有抽屉使用 `role="dialog"`、`aria-modal="true"`、可见焦点、Escape 关闭和焦点恢复。提交期间禁用按钮，错误显示在当前操作区域，不用仅依赖 Toast。

## API 边界

路由命名遵循现有 `/api/admin/*` 与 `/api/me/*` 约定。

主要接口组：

- `/api/admin/reviews`：列表、汇总、批量审核和单条详情。
- `/api/admin/reviews/:id/actions/*`：通过、拒绝、隐藏、恢复和商家回复。
- `/api/admin/support/tickets`：列表、汇总和详情。
- `/api/admin/support/tickets/:id/actions/*`：分配、优先级、状态、公开回复和内部备注。
- `/api/me/support/tickets`：登录用户工单列表、详情和回复。
- `/api/support/tickets/lookup`：匿名安全查询。
- `/api/admin/marketing/campaigns`：活动列表、草稿和版本。
- `/api/admin/marketing/campaigns/:id/actions/*`：发布、暂停、恢复、结束和复制。
- `/api/admin/marketing/campaigns/:id/preview`：价格预览与冲突结果。

所有后台动作携带 `operationId`。批量评论操作使用同一个操作 ID 和明确的评论 ID 集合，重复提交不产生部分重复结果。

## 错误处理与安全

- 非管理员后台请求返回 403。
- 非工单所有者请求返回统一 404，避免资源枚举。
- 匿名工单查询失败返回统一错误，并按会话与来源地址限频。
- 校验错误返回稳定错误码和字段列表。
- 事务中的校验失败必须回滚所有数据库写入。
- 公开接口不返回内部备注、审核载荷、管理员邮箱或完整审计 payload。
- 评论和工单正文统一进行长度限制与输出转义。
- 不进行模型探测、并发智能体调用或外部内容审核请求。

## 测试策略

### 数据库与仓储

- 迁移可重复执行，历史评论默认发布，历史工单保持 `open`。
- 评论状态流、批量操作、回复和前台可见性。
- 工单消息可见性、分配、优先级、状态流和客户隔离。
- 优惠版本、乐观锁、发布投影、冲突检测和价格计算一致性。
- 校验失败与重复操作不产生部分写入。

### API

- 管理员与普通用户权限。
- 评论混合审核和风险规则。
- 工单匿名查询保护、客户回复与内部备注隔离。
- 优惠草稿、发布、暂停、恢复、结束和冲突错误。
- `operationId` 幂等重放与不一致重放拒绝。

### UI

- 评论筛选、批量审核、商家回复和列表同步。
- 工单分配、公开回复、内部备注和客户侧追踪。
- 优惠分段编辑、预览、冲突提示和发布状态同步。
- 抽屉焦点、Escape、键盘操作和 375px 移动端无横向溢出。

### 回归

- `npm run test:api`。
- `npm run test:ui`。
- 所有 Playwright 测试保持 `--workers=1`。
- 测试结束后恢复 fixture，清除明确生成的上传产物。

## 非目标

- 外部 AI 内容审核。
- 实时 WebSocket 客服聊天。
- 多管理员双人审批。
- 秒杀、会员价和推荐位活动。
- 外部客服系统、邮件或短信集成。
- 任意旧活动版本的一键回滚。

## 验收标准

- 三个模块均可从现有后台页签访问，且只对管理员开放。
- 评论公共展示严格遵循审核状态，商家回复可追踪。
- 客户和客服可以围绕同一工单持续公开沟通，内部备注不会泄露。
- 优惠活动从草稿到发布的运行结果与购物车价格预览一致。
- 所有状态变化、批量操作和发布行为可审计且幂等。
- 完整 API/UI 测试通过，移动端和键盘交互满足现有后台标准。
