# 袜子商城售后、支付与后台管理设计文档

- 日期：2026-07-24
- 主题：在客服与信任体系之后，继续建设真实商城闭环
- 开发策略：以售后/退换货流程为主，支付模拟与后台管理作为配套阶段
- 分支基础：依赖 `feature/socks-customer-trust` 中的信任中心、客服工单和全站壳层

## 1. 目标

把当前袜子商城从“可浏览、可加购、可结算、可查看订单、可提交客服工单”的演示商城，升级为更完整的真实商城闭环。用户应能围绕订单完成付款、发起售后；管理员应能在演示后台查看订单、客服工单、售后单和库存预警，并推进关键状态。

本阶段以售后/退换货为主线，因为它天然承接现有订单历史、订单详情、客服与退换政策。支付模拟和后台管理作为配套模块接入同一套订单生命周期，不引入真实支付服务、真实客服系统或复杂权限系统。

## 2. 当前上下文

项目已经具备：

- SQLite-backed 商品、SKU、库存、购物车、用户、地址、订单、营销数据
- 订单生命周期基础状态：待支付、已支付、处理中、已发货、已送达、已取消
- 订单详情页和订单历史页
- 客服与信任中心设计和实现分支
- `support_tickets` 客服工单表和联系入口
- 顶部导航、页脚、多语言和单页多视图壳层

现有系统里售后、支付和后台管理还不完整：

- 用户无法从订单发起退换货
- 订单付款仍是简单状态按钮，不像真实支付流程
- 没有统一后台入口处理订单、售后、客服和库存预警

## 3. 阶段拆分

### PR 1：售后/退换货流程

交付一个可用的售后闭环：

- 用户从订单详情或订单历史发起售后申请
- 可选择订单商品、尺码、数量和售后原因
- 后端创建售后单
- 用户可查看售后进度
- 售后单与订单、用户、客服工单建立可追踪关系

### PR 2：支付模拟流程

交付更真实的支付体验：

- 结算后订单进入待支付
- 新增支付页或支付面板
- 用户可模拟支付成功、支付失败、重试、取消
- 支付结果写入订单时间线
- 订单状态和支付状态分离但保持同步规则

### PR 3：后台管理入口

交付演示级运营后台：

- 查看订单列表
- 查看售后单列表
- 查看客服工单列表
- 查看库存预警
- 推进订单状态
- 审核售后申请
- 不做复杂管理员账号系统，先使用演示管理员入口

## 4. 总体架构

继续采用现有 Node HTTP + SQLite + 单页 HTML 的架构。

新增视图建议：

- `view=return`：用户发起售后申请
- `view=returns`：用户查看自己的售后历史
- `view=payment`：用户支付模拟页
- `view=admin`：演示后台入口

新增后端模块建议：

- `lib/repositories/returns.js`
- `lib/repositories/payments.js`
- `lib/repositories/admin.js`

新增 SQLite 表建议：

- `return_requests`
- `return_request_items`
- `payment_attempts`
- 可选：`admin_audit_events`

## 5. 售后/退换货流程设计

### 5.1 用户入口

订单详情页新增：

- “申请退换”按钮
- 每个订单商品旁展示可售后数量
- 已取消订单不可申请售后
- 未支付订单不可申请售后
- 已提交售后的商品数量不应重复超过原订单数量

订单历史页新增：

- 有可售后商品时显示“申请售后”
- 已有售后单时显示“查看售后进度”

信任中心退换政策 section 中增加“从订单发起售后”的引导链接。

### 5.2 售后申请表单

字段：

- 订单号
- 商品行
- 尺码
- 数量
- 售后类型：退货退款、换货、仅退款
- 原因：尺码不合适、质量问题、错发漏发、不喜欢、其他
- 说明
- 联系方式

本阶段不做图片上传，避免引入文件存储和合规问题。

### 5.3 售后状态

状态流：

- `submitted`：已提交
- `reviewing`：审核中
- `approved`：已通过
- `rejected`：已拒绝
- `completed`：已完成
- `cancelled`：用户取消

规则：

- 用户创建后默认为 `submitted`
- 后台可把 `submitted` 推进到 `reviewing`
- 后台可把 `reviewing` 推进到 `approved` 或 `rejected`
- 后台可把 `approved` 推进到 `completed`
- 用户只能取消 `submitted` 或 `reviewing`

### 5.4 售后与客服工单关系

售后申请可自动生成一条关联客服工单，或在售后详情中提供“联系支持”入口。

推荐初版：

- 售后单本身是主记录
- 联系支持时可创建 `support_ticket`，并带上 `returnRequestId`
- 后台页面把售后单和客服工单并列展示，不强制合并为一个对象

## 6. 支付模拟流程设计

### 6.1 用户入口

结算提交订单后：

- 跳转到 `view=payment&id=<orderId>`
- 页面展示订单金额、配送信息、优惠快照和支付方式
- 用户可以选择演示支付方式：银行卡、PayPal、礼品卡

订单详情页：

- 待支付订单显示“继续支付”
- 已支付订单显示付款时间和支付方式
- 支付失败订单显示“重试支付”

### 6.2 支付状态

新增支付状态：

- `requires_payment`
- `processing`
- `succeeded`
- `failed`
- `cancelled`

订单状态同步规则：

- 新订单默认 `pending_payment`
- 支付成功后订单变为 `paid`
- 支付失败后订单仍保持 `pending_payment`
- 用户取消支付可保持 `pending_payment` 或取消订单
- 后台取消订单后支付不可继续

### 6.3 支付尝试记录

每次点击模拟支付都创建 `payment_attempts`：

- `id`
- `order_id`
- `user_id`
- `method`
- `status`
- `amount`
- `failure_reason`
- `created_at`
- `updated_at`

这样订单历史可以看到支付尝试，不会只有一个前端按钮状态。

## 7. 后台管理入口设计

### 7.1 入口与权限

新增 `view=admin`。

初版使用演示管理员入口：

- 不新增复杂角色权限系统
- 可通过固定演示开关或当前登录用户邮箱判断管理员
- 未登录用户进入后台时提示登录
- 非管理员用户显示无权限提示

如果后续要真实化，再扩展 `users.role` 字段。

### 7.2 后台模块

订单管理：

- 列表展示订单号、用户、金额、状态、创建时间
- 可进入订单详情
- 可推进订单状态：已支付、处理中、已发货、已送达、取消

售后管理：

- 列表展示售后单号、订单号、用户、类型、原因、状态
- 可审核通过、拒绝、完成
- 状态变更写入售后时间线

客服工单：

- 展示 `support_tickets`
- 可查看用户消息、联系方式、关联订单或售后单
- 初版可只支持标记状态，不做回复系统

库存预警：

- 展示低库存 SKU
- 展示售罄 SKU
- 可链接到商品详情
- 初版不做后台改库存，避免和库存校验规则冲突

### 7.3 后台视觉

后台不走营销页视觉，采用高密度运营表格：

- 顶部保留商城壳层
- 主区使用 dashboard 布局
- 左侧或顶部 tab：订单、售后、客服、库存
- 表格优先，卡片辅助
- 黑白灰风格继续统一

## 8. API 设计

### 8.1 售后 API

`GET /api/me/returns`

- 返回当前用户售后历史
- 未登录返回 `AUTH_REQUIRED`

`POST /api/returns`

- 创建售后申请
- 校验订单归属、订单状态、商品数量和可售后数量

`GET /api/returns/:id`

- 返回售后详情
- 只能本人或管理员查看

`PATCH /api/returns/:id/status`

- 管理员推进售后状态
- 用户只允许取消自己的未完成售后

### 8.2 支付 API

`POST /api/orders/:id/payments`

- 创建支付尝试
- 支持模拟成功或失败
- 成功时推进订单到 `paid`

`GET /api/orders/:id/payments`

- 返回订单支付尝试历史

### 8.3 后台 API

`GET /api/admin/summary`

- 返回订单、售后、客服、库存预警摘要

`GET /api/admin/orders`

- 返回后台订单列表

`GET /api/admin/returns`

- 返回后台售后列表

`GET /api/admin/support-tickets`

- 返回客服工单列表

`GET /api/admin/stock-alerts`

- 返回低库存和售罄 SKU

## 9. 错误码

售后：

- `RETURN_ORDER_NOT_FOUND`
- `RETURN_ORDER_NOT_ELIGIBLE`
- `RETURN_ITEM_NOT_FOUND`
- `RETURN_QUANTITY_INVALID`
- `RETURN_QUANTITY_EXCEEDED`
- `RETURN_REASON_REQUIRED`
- `RETURN_STATUS_INVALID`
- `RETURN_TRANSITION_INVALID`

支付：

- `PAYMENT_ORDER_NOT_FOUND`
- `PAYMENT_ORDER_NOT_PAYABLE`
- `PAYMENT_METHOD_INVALID`
- `PAYMENT_ATTEMPT_FAILED`

后台：

- `ADMIN_AUTH_REQUIRED`
- `ADMIN_FORBIDDEN`
- `ADMIN_RESOURCE_NOT_FOUND`

继续沿用标准 API 错误信封。

## 10. 数据一致性

售后数量校验必须以后端为准：

- 从订单快照读取原始商品数量
- 汇总同一订单商品已提交且未取消的售后数量
- 新申请数量不能超过剩余可售后数量

支付状态必须以后端为准：

- 前端只发起支付尝试
- 后端创建 `payment_attempts`
- 后端更新订单状态和时间线

后台状态推进必须复用现有订单生命周期规则：

- 不允许从已取消推进到已发货
- 不允许跳过关键状态
- 不允许重复完成已完成售后

## 11. 多语言

用户侧售后、支付页面需要中英文。

后台管理初版也提供中英文基础文案，但以运营可读为优先：

- 状态标签
- 按钮
- 空状态
- 错误提示
- 表格列名

## 13. 验收标准

总体验收：

- 用户能完成下单、支付模拟、查看订单、发起售后、查看售后进度
- 后台能查看订单、售后、客服工单和库存预警
- 支付、订单、售后状态由后端持久化
- 用户侧和后台侧都不依赖 JSON 作为真实状态源
- 不破坏现有商品、购物车、营销、客服与信任中心

分阶段验收：

- PR 1 合并前，售后主流程必须可独立使用
- PR 2 合并前，支付流程必须和订单生命周期一致
- PR 3 合并前，后台必须能处理至少订单状态和售后状态

## 14. 明确不做

- 真实支付网关
- 真实退款
- 真实物流逆向取件
- 文件上传凭证
- 复杂 RBAC 权限系统
- 客服实时聊天
- 后台商品编辑器
- 后台库存手工修改

这些能力可以作为后续真实化阶段，但不进入本轮三个 PR。
