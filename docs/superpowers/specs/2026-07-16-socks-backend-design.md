# 袜子商城后端接口设计文档

- 日期：2026-07-16
- 主题：为 `socks-product-list.html` 增加真实后端接口
- 方案：`Node.js + 原生 http + JSON 文件持久化`

## 1. 目标

为当前的袜子商城列表页补齐一套最小但真实可用的后端能力，使前端不再依赖页面内硬编码商品数据和前端伪购物车逻辑，而是通过 HTTP 接口获取商品列表、执行筛选排序、读取购物车并写入购物车。

本次目标聚焦于“让页面接上真实后端”，而不是搭建完整电商系统。

需要达成的结果：

- 商品列表改为通过后端接口获取
- 分类筛选和排序改为通过接口参数驱动
- 加入购物车改为真实调用后端写接口
- 购物车数据真实落盘，不只存在浏览器内存
- 保持当前页面的交互和视觉风格基本不变
- 保持项目足够轻量，适合当前单页面演示项目继续迭代

## 2. 范围

本次设计包含：

- 一个本地可启动的 Node.js HTTP 服务
- 商品数据读取接口
- 购物车读取接口
- 购物车写入接口
- 前端列表页与这些接口的联调
- 基础接口测试与前端联调测试

本次不包含：

- 用户登录
- 多用户购物车隔离
- 订单创建
- 支付
- 库存扣减
- 后台管理系统
- 数据库接入

## 3. 方案选择

### 3.1 采用方案

采用 `Node.js + 原生 http + JSON 文件持久化`。

原因：

- 当前仓库非常轻，只包含静态 HTML 和 Playwright 测试
- 这次重点是“接真实接口”，不是引入框架体系
- 原生 `http` 足以覆盖当前接口规模
- JSON 文件落盘可以满足“真实后端”的要求，同时避免过早引入数据库

### 3.2 未采用方案

#### Express + JSON

优点是路由写法更直接，但当前接口量很小，引入额外依赖收益有限。

#### Express + SQLite

更接近正式项目，但超出本次目标，会把任务从“接真实接口”扩大成“服务端基础设施搭建”。

## 4. 架构概览

系统分为三层：

1. 前端页面层
   `socks-product-list.html` 负责展示商品、发起筛选排序请求、调用购物车接口并反馈结果
2. HTTP 接口层
   Node.js 服务负责处理请求、做参数校验、返回 JSON
3. 数据持久化层
   商品与购物车数据以本地 JSON 文件存储

整体数据流：

- 页面加载时调用 `GET /api/products`
- 用户切换分类或排序时重新调用 `GET /api/products`
- 用户点击加入购物车时调用 `POST /api/cart/items`
- 如需读取购物车状态，则调用 `GET /api/cart`

## 6. 接口设计

### 6.1 `GET /api/products`

用途：

- 返回商品列表
- 支持分类筛选
- 支持排序

请求参数：

- `filter`
  可选值：`all`、`sport`、`daily`、`crew`、`no-show`
- `sort`
  可选值：`recommended`、`price-asc`、`price-desc`、`newest`

返回结构：

```json
{
  "items": [
    {
      "id": "sock-01",
      "series": "Cotton Daily",
      "title": "极简中筒袜",
      "categoryKey": "crew",
      "categoryLabel": "中筒袜",
      "price": 39,
      "originalPrice": 59,
      "discount": "32% OFF",
      "description": "柔软透气面料，适合日常通勤与居家穿着。",
      "sizes": ["35-38", "39-42", "43-45"],
      "isRecommended": true,
      "releaseDate": "2026-07-15",
      "visualTone": "#f7f7f7",
      "visualShadow": "#d4d4d4",
      "visualAccent": "#c3c3c3",
      "visualPattern": "minimal"
    }
  ],
  "meta": {
    "filter": "all",
    "sort": "recommended",
    "count": 6
  }
}
```

规则：

- `filter` 缺省时默认 `all`
- `sort` 缺省时默认 `recommended`
- `recommended` 排序规则：
  - 先按 `isRecommended` 降序
  - 再按 `releaseDate` 降序
- 返回结果中的 `count` 必须等于当前可见商品数

### 6.2 `GET /api/cart`

用途：

- 读取当前匿名购物车内容

返回结构：

```json
{
  "items": [
    {
      "productId": "sock-02",
      "size": "43-45",
      "quantity": 1
    }
  ],
  "meta": {
    "itemCount": 1
  }
}
```

规则：

- 当前项目只有一个匿名购物车
- `itemCount` 表示购物车条目总数，不是商品种类数以外的复杂统计

### 6.3 `POST /api/cart/items`

用途：

- 向购物车新增一个商品条目

请求体：

```json
{
  "productId": "sock-02",
  "size": "43-45",
  "quantity": 1
}
```

写入规则：

- `productId` 必须存在于商品数据中
- `size` 必须属于该商品允许的 `sizes`
- `quantity` 若缺省则按 `1` 处理
- 若购物车中已存在相同 `productId + size`，则累加数量

成功返回：

```json
{
  "ok": true,
  "item": {
    "productId": "sock-02",
    "size": "43-45",
    "quantity": 1
  },
  "meta": {
    "itemCount": 1
  }
}
```

失败返回：

- `400`：请求体不合法、尺码不合法、数量不合法
- `404`：商品不存在
- `500`：读写文件失败

## 7. 数据设计

### 7.1 商品数据

商品数据从当前前端内嵌数组迁移到 `data/products.json`。

这份数据继续保留：

- 页面渲染所需字段
- 筛选排序所需字段
- 当前 SVG 商品图生成所需字段

这样前端仍然可以根据接口返回动态渲染现在的卡片视觉。

### 7.2 购物车数据

`data/cart.json` 采用简单结构：

```json
{
  "items": []
}
```

设计原则：

- 结构尽量简单
- 后续可平滑扩展成数据库
- 保持当前演示项目易读、易改

## 8. 前端改造设计

### 8.1 页面初始化

页面启动后不再直接使用内嵌 `products` 作为显示数据源，而是：

1. 读取当前激活的 `filter` 和 `sort`
2. 请求 `GET /api/products`
3. 根据返回数据渲染商品列表和结果数

### 8.2 筛选与排序

点击筛选或排序按钮后：

1. 更新前端当前状态
2. 发起新的 `GET /api/products`
3. 用返回结果更新页面

这保证了：

- 当前页面行为和真实后端一致
- 测试覆盖的是联调结果，不是前端本地模拟逻辑

### 8.3 加入购物车

点击加入购物车时：

1. 读取当前卡片选中的尺码
2. 调用 `POST /api/cart/items`
3. 成功后显示 `已加入购物车`
4. 1500ms 后恢复按钮文字

当前阶段不要求页面上展示购物车数量角标，但接口必须真实写入成功。

### 8.4 空状态

当 `GET /api/products` 返回空数组时：

- 页面显示当前已有空状态文案 `当前分类暂无商品`
- 结果数显示 `0`

## 9. 服务端行为设计

### 9.1 静态资源托管

服务端不仅提供 API，也负责托管：

- `socks-product-list.html`
- `socks-product-card.html`
- 测试所需静态页面

这样 Playwright 可以直接访问本地 HTTP 服务，而不是 `file://` 页面。

### 9.2 JSON 读写

服务端每次请求时直接读取 JSON 文件，不做复杂缓存。

理由：

- 当前数据量非常小
- 逻辑更直观
- 更容易验证持久化行为

### 9.3 错误处理

服务端需要统一返回 JSON 错误响应，例如：

```json
{
  "ok": false,
  "error": {
    "code": "INVALID_SIZE",
    "message": "Size is not available for this product."
  }
}
```

要求：

- 参数错误要返回明确错误码
- 文件读写失败要返回 `500`
- 前端对失败至少要回退按钮文案，不让交互卡死

## 10. 测试设计

### 10.1 API 测试

新增 `tests/api.spec.js`，验证：

- `GET /api/products` 默认返回 6 件商品
- 分类筛选正确
- 排序结果正确
- `GET /api/cart` 可正常返回
- `POST /api/cart/items` 成功写入
- 非法 `productId` / `size` / `quantity` 返回正确错误

### 10.2 前端联调测试

列表页测试切换为跑在真实 HTTP 服务之上，重点验证：

- 页面能通过后端拉到商品
- 筛选排序仍正常工作
- 加入购物车会触发真实接口成功路径
- 页面交互和视觉回归不被破坏

### 10.3 数据隔离

测试需要避免污染真实购物车数据。

实现要求：

- 测试开始前重置 `cart.json`
- 或服务端提供仅测试环境使用的独立数据文件路径

本次更推荐第二种：服务端支持通过环境变量指定 `data` 目录，测试跑专用测试数据目录。

## 11. 运行方式

计划增加脚本：

- `npm run dev`
  启动本地 HTTP 服务
- `npm test`
  启动或接入测试服务后运行 Playwright

如果测试需要自动拉起服务，优先在 Playwright 配置中增加 `webServer`，让测试自动启动后端。

## 12. 约束与边界

- 保持技术栈简单，不引入 Express
- 保持文件编码 UTF-8
- 保持中文直接写入，不使用 `\uXXXX`
- 不破坏现有单卡页
- 新后端逻辑优先服务列表页，但静态资源托管允许单卡页继续访问

## 13. 验收标准

### 13.1 功能验收

- 列表页加载时通过真实接口获取商品
- 分类和排序通过真实接口返回结果
- 加入购物车调用真实接口并持久化写入
- 空分类时页面显示空状态

### 13.2 技术验收

- 服务端可本地启动
- 商品和购物车数据从 JSON 文件读取或写入
- Playwright 测试跑在 HTTP 服务上
- 所有测试通过

### 13.3 范围验收

- 只做匿名购物车
- 不扩展到订单、登录、支付
- 不引入重量级后端框架或数据库

## 14. 实现备注

- 这是一个“从纯静态演示页过渡到真实接口驱动页面”的阶段性版本
- 重点是把商品列表和购物车动作接到真实后端
- 后续如果需要，再把 JSON 持久化升级为数据库
